# Work&PlayVPN — подарки

Патч для версии со стабильными Happ-ключами (a666433 / миграция a310d5e8c742).
Новая миграция: b420e6f9d853. Архив не содержит токенов, .env или серверных override.

## Что добавлено

- Отдельная карточка «Подарки» на главной Mini App и кнопка в главном меню бота.
- Купить Basic/Mobile на сроки и по ценам доступного текущего каталога; trial и дополнительные слоты не продаются в подарок.
- Проверить код, затем явно подтвердить активацию. Оплаченный код не имеет срока активации.
- «Мои подарки»: купленные и активированные, статусы счетов, копирование кода, передача через Telegram, загрузка более ранних подарков.
- Ссылка вида https://t.me/workplayvpn_bot?start=gift_... регистрирует получателя и открывает экран подтверждения; сам переход по ссылке подарок не расходует.
- Срок подписки начинается при активации. Действующая подписка того же типа продлевается; другая подписка, постоянные Happ-ключи и список устройств сохраняются. Нового третьего ключа не будет.
- Подарок не добавляет платные дополнительные слоты. Применяется включённый лимит купленного тарифа и существующая общая модель устройств Basic/Mobile.
- В приватный Informer приходят покупка и активация. Подарочные коды в уведомления не включаются.

Это единый механизм через Mini App: кнопка бота «Подарки» открывает тот же раздел, чтобы покупки и активация не расходились между двумя интерфейсами.

## Защита и ограничения

- Код появляется только после серверного подтверждения платежа существующим платёжным провайдером. Возврат браузера со страницы оплаты сам по себе не выдаёт подарок.
- Ровно один сертификат на платёж; повторные webhook не выдают дополнительные подарки.
- Сервер сохраняет тип, срок и включённый лимит на момент создания заказа, независимо от последующих изменений каталога.
- Активация блокирует строку сертификата в PostgreSQL. При двух получателях выигрывает один. Повтор того же запроса получателем не продлевает подписку второй раз.
- Сбой при добавлении VPN-доступа откатывает выдачу и активацию; подарок остаётся доступен для повторной попытки.
- 120 бит случайно выглядящего кода, HMAC-поиск; открытый код в БД не хранится. Покупатель может повторно получить свой код до активации.
- До 10 попыток проверки/активации за 15 минут на аккаунт. Неудачные попытки сохраняются после перезапуска, смены сессии и отката запроса. Проверка и подтверждение считаются двумя попытками.
- До 5 одновременно ожидающих оплаты подарочных заказов и до 20 новых заказов за 24 часа на покупателя. Повтор запроса с тем же idempotency_key не создаёт новый счёт. Счёт действует 24 часа; это не срок активации оплаченного подарка.
- Покупатель не может активировать собственный подарок. Реферальные начисления на подарки отсутствуют.
- Доступ к спискам и покупке — только по проверенной Telegram Web App авторизации; нет доверия к Telegram ID из тела запроса. Покупатель видит свои коды, получатель — историю своих активаций.
- Mobile сохраняет существующий rollout по внутренним User ID. Если получателю Mobile недоступен, подарок не расходуется; это ограничение нужно учитывать при покупке для другого человека.
- Тестовые подарки помечены и не активируются после переключения сервиса в live. Их не следует передавать реальным покупателям.
- Подарочный платёж не активирует подписку покупателя и не запускает отправку VPN-профиля покупателю. Обычная оплата не отменяет подарочные счета, и наоборот.

Код/ссылка — предъявительский секрет: кто первым подтвердит активацию, тот получит подарок. Техническая защита не определяет настоящего человека и не исключает несколько Telegram-аккаунтов. Не публикуй коды, полные ссылки или .env в логах и переписке поддержки.

**SUBSCRIPTION_TOKEN_SECRET должен оставаться постоянным и попадать в резервные копии конфигурации.** Он нужен для восстановления и поиска подарочных кодов, как и для текущих ключей. Не меняй его после выпуска подарков без отдельной процедуры ротации. При потере секрета обычной копии БД недостаточно для восстановления кодов.

Автоматические возвраты денег, chargeback и административная отмена уже активированного подарка в этот патч не входят. Такие случаи требуют ручного рассмотрения; не обещай автоматический возврат в интерфейсе. Миграция не удаляет текущие данные. Автоматический downgrade намеренно запрещён: финансовую историю нельзя удалять ради отката кода.

## 1. На ноутбуке — распаковка и тесты

Сначала убедись, что предыдущие изменения сохранены в Git. Если появились посторонние новые правки, не перезаписывай их архивом до проверки.

Запускать в корне WorkPlayVPN, PowerShell:

```powershell
$ErrorActionPreference = "Stop"
$archivePath = (Resolve-Path -LiteralPath .\WorkPlayVPN-gifts-2026-10-05.zip).Path
Expand-Archive -LiteralPath $archivePath -DestinationPath . -Force -ErrorAction Stop

$backendSource = Join-Path (Get-Location).Path "backend"
$opsSource = Join-Path (Get-Location).Path "ops"
docker compose --profile testing run --rm --pull never --volume "${backendSource}:/app:ro" --volume "${opsSource}:/ops:ro" tests
if ($LASTEXITCODE -ne 0) { throw "Тесты backend не прошли; сервер пока не обновляем" }

$botSource = Join-Path (Get-Location).Path "bot"
docker compose run --rm --no-deps --pull never --volume "${botSource}:/app:ro" --entrypoint python bot -m unittest discover -s tests -v
if ($LASTEXITCODE -ne 0) { throw "Тесты бота не прошли; сервер пока не обновляем" }

git -c core.whitespace=cr-at-eol diff --check
if ($LASTEXITCODE -ne 0) { throw "Проверка изменений не прошла" }
```

Новых зависимостей нет. Используем готовые тестовые образы, без --build: это не требует повторного запроса Docker Hub, на котором раньше возникал TLS handshake timeout. Если образ tests отсутствует, сначала потребуется обычная сборка при доступном Docker Hub.

Локально проверены 99 targeted backend тестов и 54 теста бота. Четыре проверки реальных PostgreSQL-блокировок здесь пропущены (нет PostgreSQL), включая гонку двух получателей; в Docker тестовой БД она должна выполниться. Полный backend suite и настоящая платёжная интеграция здесь не запускались. Старое предупреждение Starlette не является падением.

Сначала пришли результат тестов. Следующие пункты — только после успешной проверки.

## 2. Добавить только файлы патча в Git

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
$archive = [System.IO.Compression.ZipFile]::OpenRead($archivePath)
try {
    $patchFiles = @($archive.Entries | Where-Object { $_.Name -ne "" } | ForEach-Object { $_.FullName })
} finally { $archive.Dispose() }

git add -- $patchFiles
if ($LASTEXITCODE -ne 0) { throw "Не удалось добавить файлы" }
git -c core.whitespace=cr-at-eol diff --cached --check
if ($LASTEXITCODE -ne 0) { throw "Проверка staged изменений не прошла" }
git diff --cached --stat
```

Проверь, что в staged нет .env, токенов, локальных БД и архивов. Затем:

```powershell
git diff --cached --quiet
if ($LASTEXITCODE -eq 1) {
    git commit -m "Add paid gifts with atomic redemption and abuse protection"
    if ($LASTEXITCODE -ne 0) { throw "Коммит не создан" }
} elseif ($LASTEXITCODE -ne 0) {
    throw "Не удалось проверить staged изменения"
}
git log -1 --oneline
git push origin main
if ($LASTEXITCODE -ne 0) { throw "Не удалось отправить коммит" }
```

Если изменений для нового коммита нет, проверь git show --stat HEAD: возможно, коммит уже создан. Не добавляй все untracked через git add .; среди них могут быть архивы, тестовые БД и секреты.

## 3. Сервер — после проверок и push

Перед миграцией проверь актуальный успешный бэкап **удалённой Timeweb БД** и сохранность секретов. Не используй локальную БД сервиса database как бэкап production. Не меняй .env, TLS и docker-compose.override.yml: данный патч их не затрагивает.

```bash
cd /opt/workplayvpn
set -e
git pull --ff-only origin main
docker compose build backend bot informer-worker payment-fulfillment-worker
docker compose run --rm --no-deps --volume "${PWD}/backend:/app:ro" backend alembic upgrade head
docker compose up -d --no-deps backend bot informer-worker payment-fulfillment-worker
docker compose ps backend bot informer-worker payment-fulfillment-worker
docker compose logs --tail=80 backend bot informer-worker
```

Предупреждение об orphan workplayvpn-xray не устраняем через --remove-orphans: не удаляем рабочую ноду. Миграция выполняется с production environment backend, где уже настроен Timeweb и TLS. Не запускай её вручную для другой БД.

Статика Mini App подключена к Caddy bind-mount и обновляется после git pull. Файлы получили новые cache-busting версии. Закрой Mini App полностью и открой заново. Если у тебя статика вместо bind-mount встроена в отдельный образ, обнови этот образ по своей текущей схеме; Caddyfile патч не меняет.

Безопасная диагностика (не выводит пароли):

```bash
docker compose exec -T backend python - <<'PY'
from sqlalchemy import text
from app.db.session import engine
print("Host:", engine.url.host)
with engine.connect() as db:
    print("Migration:", db.scalar(text("SELECT version_num FROM alembic_version")))
    print("Gifts:", db.scalar(text("SELECT to_regclass('public.gift_certificates')")))
    print("Attempt limits:", db.scalar(text("SELECT to_regclass('public.gift_attempt_windows')")))
PY
```

Ожидаем Timeweb host, b420e6f9d853 и обе новые таблицы.

## 4. Ручная приёмка в текущем test-режиме

1. В боте появилась отдельная кнопка «Подарки», на главной Mini App — отдельная карточка.
2. Купить Basic-подарок. До подтверждённой тестовой оплаты нет кода. После оплаты код появился, но подписка покупателя не продлилась.
3. Повторно проверить статус/перезагрузить приложение: один платёж, один подарок, один код. При повторном callback нет второго уведомления о покупке.
4. Попытаться активировать его с аккаунта покупателя: отказ, подарок остаётся готовым.
5. Передать ссылку жене. В боте получателя «Открыть подарок» ведёт на подтверждение. До нажатия «Активировать на моём аккаунте» никаких изменений.
6. Активировать на втором аккаунте: появился/продлился Basic; Mobile, устройства и постоянные ссылки не изменились. Покупатель видит «Активирован», получатель — запись в своей истории.
7. Повторить активацию тем же получателем: срок второй раз не увеличился. Попробовать другим аккаунтом: отказ.
8. Проверить Mobile на аккаунте, которому он разрешён; отдельно проверить отказ для аккаунта вне pilot без расходования кода, если rollout ограничен.
9. Проверить правильные «Назад», копирование кода, переданную ссылку, список ожидающих оплаты счетов и отсутствие лишней «подписки покупателя» в главном меню.
10. Проверить приватные уведомления Informer о покупке и активации. Коды и ссылки-подарки в уведомлениях не должны появляться.

Не переключай production на live исключительно ради проверки этого патча. Переход реального эквайринга — отдельный шаг после одобрения магазина. Тестовые подарки останутся тестовыми, не превращаются в оплаченные live-подарки.
